技術挑戰
與解法
  • 發佈作業不可重複執行：對外發佈具不可逆性，任務重試或使用者重複觸發皆不得產生重複貼文。以任務認領機制與確定性識別碼確保冪等，並於作業結束後進行狀態核對。
  • 長時間背景作業的狀態呈現：產製與發佈耗時且跨越多個階段，需在前端如實反映進度、失敗與完成，並處理使用者中途離開頁面後回訪之情境。
  • 多租戶資料隔離：平台為多商家共用，須確保任一商家僅能存取自身資料；為此定義單一的擁有權判定來源，所有資料查詢一律以該來源為依據。
  • 多平台差異吸收：四個社群平台之授權模式、內容格式與發佈限制皆不相同，需在共用之發佈流程下吸收平台差異。
  • 品質治理：以強制測試先行（TDD）方式開發，累計 206 個測試檔；並以 knip 清理死碼與多餘依賴，另開啟編譯器未使用變數檢查作為第二道防線。

  • 遷移範圍之協調與議定：與客戶端及原開發團隊共同盤點各伺服器上雙方爬蟲之分布後議定遷移方式 —— 本方爬蟲佔多數之 2 台由本方留用、另一方自行遷出；其餘伺服器則由本方新建環境承接本方爬蟲，藉此將雙方的遷移成本與服務中斷風險降至最低。
  • 雲端伺服器建置與管理：管理 8 台 AWS EC2 生產伺服器 —— 其中 6 台為自行規劃建置（含 S3 儲存與安全群組之進出流量規則設定），並依既有爬蟲與目標網站之對應關係完成資產盤點後遷入；另 2 台為留用之既有環境，因無遷移需求、未改動即可持續運作，故未納入本次建置範圍，由本人負責後續維運。
  • 程式資產遷移：於伺服器安裝 AWS CLI，將既有程式封裝上傳 S3 後取回本機，並納入 GitLab 版本控管，建立可追溯之變更歷程。
  • 標準化本機開發環境：因部分相依套件無法於本機作業系統執行，自行撰寫 Dockerfile 建立與生產環境一致之 Linux 容器，使開發與測試不需在生產伺服器上進行。容器內含 Python（pyenv 管理版本）、爬蟲所需之 Linux 套件，以及特定版本之 Chrome 瀏覽器（供動態渲染與模擬使用者操作之爬蟲使用）。
    由於既有爬蟲係由多位開發者撰寫、技術取向不一，該容器需涵蓋所有爬蟲的相依需求，以單一環境支援異質的實作方式。
  • 部署流程自動化：本機以 AWS CLI 封裝上傳 S3 → 透過 AWS Systems Manager（SSM）對 EC2 下達指令完成下載、解壓與程式更新，並將整段流程腳本化，使 6 台伺服器得以一致、可重複地部署。
  • 開發方式一致化：8 台伺服器之爬蟲程式一律於本地容器環境開發與測試，不於生產伺服器上修改程式。差異僅在部署手段 —— 自建之 6 台採 SSM 腳本化自動部署；留用之 2 台因無遷移需求、未納入本次建置範圍，後續維運更新時以 SSH 手動部署。
  • 伺服器存取方式：自建之 6 台日常以 SSM Session Manager 連線，透過 IAM 帳號權限認證，無須配發與管理金鑰對；留用之 2 台則以 SSH 金鑰連線。
  • 異常診斷：接獲資料異常通知後，以 MongoDB Compass 連線查詢該爬蟲最後寫入資料之日期，據以判斷失效時間點與影響範圍；另於 AWS 主控台建立機器監視表，掌握各伺服器之硬體使用率與存活狀態。
  • 爬蟲維護與優化：涵蓋靜態頁面擷取、動態渲染與模擬使用者操作等不同型態之修正。
技術挑戰
與解法
  • 在系統文件有限的條件下接手既有生產系統：可用資訊僅有雲端帳號與一份爬蟲部署對應清單，須自行盤點伺服器與程式資產、還原系統結構後才能規劃遷移。
  • 開發流程規範化：既有作業方式為直接於線上伺服器修改程式，缺乏版本控制與獨立測試環境。導入 GitLab 版控 + Docker 本機環境 + 腳本化部署，將開發、測試與上線三者分離。
  • 環境相依性：以容器封裝作業系統層相依套件，消除本機與生產環境的落差，使問題可在本機重現。
  • 技術債管理：重構既有程式碼、移除未使用模組、抽離共用目標。
  • 維運效率：導入 AI 協助分析目標網站結構變更、輔助定位失效原因，作為人工判讀之輔助。

專案四｜展昭國際 展覽場地互動平面圖系統（技術選型、模組化架構與圖形渲染）

技術棧React、React Router、MobX、Ant Design、PixiJS
需求背景客戶原以繪圖軟體人工製作展場平面圖，需求為改為線上系統。單一展場攤位數量最高超過 1,000 個，畫面須同時承載大量互動物件，且須考量低階裝置之可用性。
技術選型
（含實測）		渲染方案並非直覺選定，而是實際做壓力測試後決策：
　• DOM Tree：可負荷約 800+ 物件
　• SVG：可負荷約 2,000+ 物件
　• Canvas：可負荷約 4,000+ 物件
依 1,000+ 攤位並預留成長空間，最終選定 Canvas 方案（PixiJS）實作。
架構設計
  • 以「功能」而非「畫面結構」切分模組：新增攤位、選取、拖移、合併等各自為獨立模組（此專案無 HTML 結構可依循，故改變既有以版面切模組之習慣）。
  • 建立中間層統一管理：由中間層負責模組載入、各模組狀態判斷與模組間操作衝突處理；外部一律透過中間層提供之介面呼叫，達成解耦。
  • 以載入模組組合決定系統能力：依需求載入不同模組即可控制平面圖具備哪些功能，並可組成唯讀預覽模式供 App 端使用。
關鍵功能
實作
  • 復原（Undo）機制 —— 以資料驅動重繪取代命令式修改：記錄每次操作之「操作類型 + 攤位變更前後狀態」，還原時依操作類型讀取對應狀態處理。還原方式刻意採刪除後依舊狀態重新繪製，而非呼叫物件方法逐項修改屬性 —— 如此無須為每一種變更在攤位類別上開放對應的修改介面，也不需在攤位與 Undo 之間建立依賴關係，使程式結構更單純、後續維護成本更低。
  • 幾何運算：以 AABB（軸對齊邊界盒）碰撞檢測防止攤位重疊建立；貼上時自動計算位置偏移並貼齊網格。
  • 批次與剪貼簿：記憶體剪貼簿、深層複製（含圖形、參展商資料與樣式）、多選批次複製與合併。
  • 匯出：支援平面圖匯出 JPG／SVG。
  • 渲染層與狀態同步：PixiJS 管理互動圖形，與 MobX 狀態保持同步，確保表單編輯與畫布即時一致。

專案五｜公共電視 Android TV App（跨平台開發與服務介面串接）

技術棧Kotlin、Jetpack Compose（依客戶指定之原生架構）；服務介面：RESTful API + GraphQL
對應簡章工作內容第 2 項「服務介面開發」；專長第 4 項（跨語言開發能力）。已上架 Google Play，具公共媒體專案實作經驗。
擔任職責App 端 UI、互動功能與 API 串接開發（後端 API 由公視提供）。Jetpack Compose 為當時新發布之正式版架構，用於取代原有 XML 佈局，須於專案期程內完成新架構之學習與產出。
技術挑戰
與解法
  • 電視平台的操作範式差異：TV 非滑鼠點擊或觸控，而是以遙控器進行焦點轉移，須自訂完整焦點行為 ——（1）換頁時自動記錄最後選取的卡片，返回上一頁自動聚焦回該卡片；（2）網格內每一列各自維護「可聚焦目標」，並記錄離開該列時最後獲得焦點的項目，再次進入時聚焦回同一項。
  • 播放器功能：暫停／播放、從頭播放、時間軸快轉與倒轉、影片介紹 drawer 與集數列表；自動偵測並提供可選項（語音語系、字幕語系、畫質），同時支援隨選影片與直播。
  • 觀看行為數據上報：以變數記錄觀看起始時間，於特定操作時將「起始時間至當前時間」之區間回報後端 API，並將起始時間更新為當前時間後重複，藉此累積連續觀看區間紀錄。
  • 穩定性：API 錯誤捕捉與自動重試機制；自訂 Paging 支援無限捲動載入。

其他經驗

  • 美國土地租賃平台後台（React、MobX、Ant Design、Google Maps API）：地主後台功能開發與維護，歷經 V1～V3 三次改版。
  • 企業內部後台系統（React、MobX、Ant Design）：大量表單與驗證邏輯實作，以 MobX computed values 管理複雜表單狀態並優化效能。
