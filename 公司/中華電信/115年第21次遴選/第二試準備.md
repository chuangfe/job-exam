## 二、缺口分三層

### 🔴 第一層：關聯式資料庫（最缺，也最好補）

實務只碰過 NoSQL（Firestore、MongoDB），但專業測驗幾乎不可能不考 SQL。

- `SELECT` / `WHERE` / `GROUP BY` / `HAVING` / `ORDER BY`
- **JOIN 四種**（INNER／LEFT／RIGHT／FULL）與使用情境
- **正規化 1NF / 2NF / 3NF** ← 考試最常出
- 主鍵、外鍵、唯一鍵、索引
- 交易與 **ACID**、隔離級別
- 聚合函數與子查詢

### 🟡 第二層：古典後端規範

會做，但講不出教科書的名詞與規範。

- HTTP 方法語意與**冪等性定義**
- 狀態碼分類與常見碼的正確用法
- REST 設計原則（資源導向、無狀態）
- 認證授權：Session vs JWT、OAuth 2.0 授權流程
- Cookie 屬性：`HttpOnly`、`Secure`、`SameSite`

### 🟢 第三層：其實會，只是沒對上名詞

**這層不用學，只要背名詞對照。**

| 實際做過的事 | 正式名稱 |
|---|---|
| claim 機制 + 確定性 id 防止重複發佈 | **冪等性（Idempotency）** |
| 作業結束後的狀態核對 | **Reconciliation** |
| compare-and-set 更新狀態 | **樂觀鎖 / CAS** |
| Cloud Tasks 背景任務 | **訊息佇列 / 非同步處理** |
| 多商家資料隔離 | **多租戶架構（Multi-tenancy）** |
| 去重卡 | **冪等鍵 / 去重機制** |
| 捲動到底載入次頁 | **分頁（Pagination）** |
| 依地圖範圍查詢、標記聚合 | **視窗查詢 / Clustering** |
| Repository 封裝資料存取 | **資料存取層 / DAO 模式** |
| 前端輪詢背景任務狀態 | **Polling** |
| Dockerfile 統一環境 | **環境一致性 / 可重現建置** |
| 分層驗證避免重複跑測試 | **測試金字塔** |

> 💡 口試講「我做了 claim 機制」是工人；講「這是冪等性設計，我以 claim 加確定性識別碼實作」是工程師。同一件事，兩種評價。

### 為什麼直接用 Express（2026-08-31 調整）

原本設計是「先手寫 `node:http`，再進 Express」，理由是 Express 把請求解析、路由比對、
middleware 串接三件事藏起來了。**但那個順序在只剩 3 週時投報不足**：

- 筆試（選擇＋簡答）不會要你用 `node:http` 實作伺服器，考的是**知識點**本身
- 而知識點可以直接在 Express 題裡練 —— 甚至更好，因為 Express 版才能實測「冪等」

所以 [Q10](../../../練習題/Node/Q10-express-server-狀態碼與冪等/) 已改寫為 **Express 版**，
保留原本要教的三個考點並多一個：

| 考點 | 在 Q10 怎麼練 |
|------|--------------|
| **400 vs 422** | 缺 `title` 欄位 → 400（讀不懂）；`title` 是空白字串 → 422（讀懂但語意錯） |
| **404 vs 405** | 路徑不存在 → 404；路徑存在但 method 不支援 → 405 + `Allow` 標頭 |
| **body 是 stream** | `/webhook` 要對**原始 bytes** 驗 HMAC 簽章 → 不能讓 `express.json()` 先解析（測試刻意送帶多餘空白的 JSON 來抓這個錯） |
| **冪等** ⭐ 新增 | PUT／DELETE 打兩次結果相同、POST 打兩次建出兩筆 —— 手寫版測不出這個 |

> 💡 `/webhook` 驗簽那段直接對應你 Mira 系統接收 Meta inbound webhook 的情境，
> 也是 Meta／LINE／Stripe 都要求 raw body 的原因。
> 📌 [Q11 手寫路由器](../../../練習題/Node/Q11-router-手寫路由器/)、[Q12 手寫 middleware](../../../練習題/Node/Q12-middleware-手寫中介層/) **降為選配** ——
> 但 Q12 的 `答案.js` 檔頭建議讀一遍：佐證表寫了「現行系統之 API 由本人設計與實作」
> 並列出 Express 5，口試問「middleware 順序」「`next()` 在做什麼」的機率很高。

口試問的不是教科書，是**你的專案**。而你的系統文件寫得比任何教材都貼近你要講的內容 —— 每一句都對應你要回答的東西。

```

├── 專案架構.md          擁有權模型、分層結構
├── 生成貼文流程.md      生成鏈路、single-job 重構
```

⚠️ **這些文件是 SDD 流程產出的，實作細節沉在裡面。** 口試不能翻文件 —— 要在口試前讀熟，特別是 `發布貼文流程.md` 的冪等設計（那是專案一在佐證表與自傳裡的主打賣點）。

### 名詞對照（把做過的事翻譯成專業術語）

| 實際做過的事 | 正式名稱 |

### SOLID 對照（你做過，只是沒對上名詞）

| 你實際做過的設計 | 原則 |
|---|---|
| 展昭：以「功能」而非畫面結構切模組，新增攤位／選取／拖移各自獨立 | **S** 單一職責 |
| 展昭：靠載入不同模組決定系統能力（含唯讀模式），不修改既有模組 | **O** 開放封閉 |
| Mira：四個社群平台走同一套發佈流程，呼叫端不需判斷平台型別 | **L** 里氏替換 |
| Mira：留言是選配能力，只有支援的平台實作，不讓所有平台留空方法 | **I** 介面隔離 |
| Mira：Repository pattern 封裝 Firestore；Nearyou：View → ViewModel → Service → API 分層 | **D** 依賴反轉 |

### 用 AI 回頭理解自己的實作（三步法）

有程式碼、有文件、有 AI，缺的是把三者變成「能開口講」的方法。每個流程跑一輪：

**第一步：讓 AI 解釋，自己不要先猜**
在該專案開 Claude Code，指定文件與實作一起讀：
> 「讀 `doc/發布貼文流程.md` 與對應實作，用我能對面試官講的白話解釋：為什麼需要 claim？為什麼 id 要確定性？兩者各防哪一種重複？」

**第二步：關掉視窗，自己講一遍**
不看文件，把內容口述出來（錄音或講給自己聽）。**卡住的地方就是真正不會的地方** —— 這一步不能跳，「讀懂的錯覺」就是在這裡破的。

**第三步：讓 AI 當面試官追問**
> 「你是中華電信的技術面試官。針對我剛講的冪等設計，問我三個追問，包含一個我可能答不出來的。」

追問答不出來 → 回第一步。答得出來 → 換下一個流程。

**優先順序**（依口試被問到的機率）

| 順位 | 文件 | 為什麼優先 |
|:---:|------|-----------|
| 1 | `發布貼文流程.md` 冪等三情境 | 佐證表專案一與自傳的**主打賣點**，必問 |
| 2 | `專案架構.md` 擁有權模型 | 多租戶資料隔離，佐證表有寫 |
| 3 | `生成貼文流程.md` 非同步任務編排 | Cloud Tasks 是第 2、7 項的佐證 |
| 4 | `授權流程.md` 四平台 OAuth | 佐證表專案一「多平台差異吸收」 |

💡 **現成工具**：`app-template/ai-dev/.claude/skills/` 的 `explore-project` 與 `debug` 兩個 skill 本來就是為理解既有程式碼而寫的 —— 拿來讀自己的專案剛好。

## 🔴 八、最高風險事項：爬蟲專案的前開發商即為中華電信

**書面文件一律不得提及**：前開發商身分、違約、解除合約、交接品質不佳等字眼。原因：

1. **等於在應徵文件裡批評應徵對象。** 無論事實如何，讀起來就是「我來收拾你們留下的爛攤子」。
2. **審查與口試主管可能就是相關單位的人。** IT-01 用人機構是**資訊技術分公司**，正是承接這類委外開發案的單位。
3. **可能涉及尚未結清的商務爭議**，向對造書面陳述極不明智。

✅ **已處理**：佐證表與自傳僅寫「在系統文件有限的條件下接手既有生產環境」「既有作業方式為直接於線上伺服器修改」—— 陳述客觀狀態，不指涉任何一方、不評價任何關係。
⚠️ **但客戶名（亞洲指標）已具名**（2026-08-17 決定），被追問的機率因此提高，下表更要背熟。
